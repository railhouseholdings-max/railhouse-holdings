# Existing prototype audit and migration plan

Audit date: 2026-11-02. No applicable repository AGENTS.md was found at the root or ancestor project locations. This file records the prototype **before** cloud preparation; see cloud-setup.md for the resulting setup.

## Existing implementation

1. **Framework/libraries:** Next.js 16.4.3 installed, React 19, TypeScript, App Router, Tailwind CSS 4/PostCSS, ESLint 9. Runtime dependencies are Next, React and React DOM. Node's test runner runs TypeScript calculation tests. No database/auth/ORM/AI SDK is installed.
2. **Structure:** `src/app` holds server pages for Dashboard, Properties, property detail, Analyze Deal and Portfolio; shared components and responsive styles are separate. `src/domain` has plain serializable interfaces. `src/lib/calculations` holds deterministic financial functions. `src/lib/data/repository.ts` is already a natural data-access boundary, initially returning fixtures. External integrations are isolated in address/tax modules and API routes. A manifest provides install metadata but no offline worker.
3. **Data:** `src/lib/data/mock.ts` contains fictional properties/deals; `spreadsheet-example.ts` contains the historical calculator example. Fee profiles and assumptions are source code. The official Allen County rental lookup is a roughly 11 MB extracted public snapshot, bundled server-only and indexed in memory once per process. It is reference data, not user persistence.
4. **Local persistence:** Searches of application code found no localStorage, sessionStorage, IndexedDB, SQLite, runtime file writes or file-backed application database. Calculator fields, fees, tax overrides, lookup results and results live in React state. There is no Save action; edits disappear on reload/navigation. This unsaved analysis state is the main information currently at risk of being lost. Source fixtures/reference data persist as code. Excel documents are external source inputs, not production storage; the extractor is an offline maintenance script.
5. **Backend:** Next server components and three GET routes already exist: Photon US address search, current county tax lookup and server-only county rental snapshot matching. They use standard fetch, query limits, timeouts and no-store responses. There are no application writes or auth endpoints initially.
6. **Important logic:** BRRRR project cost, contingency, amortization, deterministic purchase/refinance fee profiles, prepaid interest date/rounding conventions, escrow, credits/payoffs/payment timing, whole-project recovery, operating cash flow, portfolio aggregation/returns and visual deal-strength rules. County rental taxes use projected monthly rent × parcel GRM, nearest $100, then the year-specific 2026/payable-2027 simplified tax rule, with mixed-cap limitations and zero-preserving manual overrides. Existing tests verify source reconciliations and edge cases.
7. **Preserve:** All formulas, source/reference fixtures, property domain structure, mobile navigation/layout, financial explanations, gauges, autocomplete/manual address entry, current/historical county taxes, rental tax matching and annual extraction workflow. Keep demo behavior available without credentials; never import fictional fixtures as real holdings automatically.
8. **Cloud changes needed:** Add a production-safe data source, explicit save/load for analyses, single-owner authentication/authorization, server environment config, normalized migrations/RLS, private cache handling and reproducible build/runtime guidance. Property reads should continue through the repository. No container, custom server, ORM, queue or filesystem storage is necessary.
9. **Issues:** No Git repository existed. Generated files and a large county snapshot require intentional exclusions/inclusion. No real editable property CRUD existed, so a property editor should not be invented during migration. Missing child property records must fail rather than silently zeroing financial values. Saved analyses need fee/tax settings in addition to `DealInputs`; otherwise reload changes results. Static/private data must not be prerendered or publicly cached. A single signed-in owner is sufficient; multi-user membership, roles and invitations are unnecessary. Photon demo availability and the county's external API are operational dependencies; reference-year limitations remain.

## Simplest incremental plan

- Keep Next.js/App Router and all calculation modules. Deploy that same code to Vercel with Node 24.
- Default `RAILHOUSE_DATA_MODE=demo` continues the original fixture-only experience. Explicit private mode uses Supabase PostgreSQL through a server-only repository. Missing cloud configuration/DB access fails closed; it never falls back to fictional portfolio values.
- Use Supabase Auth email/password and a single owner allowlist. Native fetch uses the documented Auth/Data APIs; no service-role key, database password or new runtime dependency is needed. A server-only, HttpOnly access-token cookie expires after at most an hour; Supabase verifies it on private reads/writes. Re-login after expiry; refresh/MFA/OAuth are outside this first increment.
- Normalize persistent entities into properties; one-to-one acquisition/rehab/financial summaries and operations; current/historical loans, leases, valuations; saved deals, fee adjustments and tax assumptions. Use typed columns for user inputs. One small JSONB column preserves a single county source lookup's evidence, which has a version-dependent external shape; it is not a dump of all app state.
- Add explicit Save/Update after calculating. A transactional, security-invoker DB function saves all analysis tables together and checks the prior revision to avoid silent overwrites. Validate/recompute the selected tax amount server-side.
- Keep the public county snapshot bundled server-only. Do not move source workbooks, generated caches, unsaved form UI state or reproducible calculation outputs into PostgreSQL.
- Keep demo fixtures and source imports untouched. Initialize/push Git only as authorized, apply schema to a new project, bootstrap the owner, run SQL security checks, test cloud save/reload locally, then deploy when the user chooses.

## Intentional limits and verification

No accounts, remote repository, cloud database, migrations on a real database or deployment were created here. Filesystem restrictions prevented creating `.git`; manual initialization is documented. The npm registry was unreachable, so a clean install/audit could not be performed here. No new dependency was added. The installed dependency tree was used for local checks, with Node 24 supplied by the development runtime. The SQL security script is version controlled but needs a real Supabase project (or compatible local Postgres/Auth schemas) before execution; there is no PostgreSQL runtime in this environment.

The sandbox also rejected binding a local production server socket (EPERM), so a fresh production-server browser smoke test could not run here. The build and automated tests passed; live Auth/PostgreSQL/RLS and production HTTP checks are explicit setup gates.
